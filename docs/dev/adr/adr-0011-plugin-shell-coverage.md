# ADR-0011: Plugin Segments Across Shells

## Status

Accepted (2026-10). B now; G as GPY's cross-shell script-segment format, a core feature.

Amended (2026-10): G is a core feature that may also power one or two built-ins; its cache is on by default with a short TTL and lives in shell variables; the trust model, output hardening, timeout constraints, trigger naming, performance budgets and the approval boundaries the work crosses are explicit. The amendment supersedes the earlier text of Decision items 2 and 3 and the Option G and Consequences text that followed from it.

Amended (2026-10): timeout, placement and scan measurements settled what Decision items 3, 5, 6, 7 and 8 left open, and the amendment rewrites items 3 and 5 to 10, the Measurements, Option G and Consequences to match. The runner is pure shell with the `/bin/sh` launcher skipped. Scripts get a clean environment, which the maintainer chose although it missed the measured cost bar (item 7). Output is sanitized once at the runner boundary, reversing item 5's earlier "escape and strip after every read, never once before a cache write". The cache is keyed on the declared inputs, `env` values and settings. The timeout, kill rules, circuit breaker and scan bound are decided; item 6 marks the parts that are not built or not measured. The earlier text claiming detect already runs in the parent shell was wrong for Zsh and is replaced. The [script segment security addendum](adr-0011-addendum-script-segment-security.md) supersedes item 5 where the two differ.

## Context

GPY is a cross-shell prompt, but community plugin segments render only in Fish. A plugin provides segments through `plugin.toml` and one Fish file per segment (`<plugin-root>/segments/<segment-id>.fish`) that defines `segment_<id>_detect` and `segment_<id>_render` and draws with the public `gpy_section_*` helpers: the `api_version = "v1"` contract in [Plugin Framework](../plugins.md#what-is-stable-in-v1).

- `gpy theme export` writes `__gpy_plugin_segment_file_<token>` for Fish only (`gpy-agent/src/theme/export/plugin_segments.rs:200-208`); `fish/core/init.fish:126-175` sources the file. `bash/core` and `zsh/core` have no loader.
- The Bash and Zsh renderers call `__gpy_segment_<id> is_last prev_bg is_first` in a `$()` subshell and skip names without that function (`bash/core/init.bash:211-220,277-305`, `zsh/core/init.zsh:177-192,244-275`).
- `entry_type = "command"` is reserved and rejected (`gpy-agent/src/plugin/registry.rs:167`).
- The only user-facing statement is one line in [CLI Reference: Plugin Commands](../../user/cli-reference.md#plugin-commands); the [shell feature matrix](../../INSTALL.md#shell-feature-matrix) opens with "Every shell renders the same segments".

Only Fish users could write a plugin, so the lack of requests from Bash and Zsh users says nothing about demand. This ADR compares the cross-shell designs on five real segments before recommending one:

- **D**: port the loader; Bash, Zsh and Fish load shell-native segment files with the `v1` names.
- **E**: `entry_type = "command"`; a program prints the segment text, run on every prompt.
- **E-cached**: the agent runs the command off the request path, caches it and repaints (ADR-0009 pattern).
- **F**: declarative trigger plus template, rendered by the agent.
- **G**: one POSIX `sh` script per segment plus a small manifest, run by each shell (cached there), with no agent involvement.

**Scope.** The segment-script contract, for third-party plugins and for GPY's own segments. The built-ins were first used below as a test bench with known-correct output; the amendment makes moving one or two of them onto G part of this decision (Decision item 2).

**Project status.** GPY has not been announced and has no users. Breaking changes are acceptable: a MAJOR schema change, changes to the `v1` manifest, no compatibility shims, and no concern for an older GPY loading a newer plugin or theme.

### Prior art

- **Starship custom commands** ([docs](https://starship.rs/config/#custom-commands), read 2026-10-23): a `[custom.<name>]` table with `command`, `when` (a shell command shown on exit 0, or a boolean), `require_repo`, `detect_files`, `detect_folders` and `detect_extensions` (checked in the working directory; `!` marks a negative match), `shell`, `use_stdin`, `os`, `format` with `$output`/`$symbol`/`$style`, and a `description` shown by `starship explain`. Commands obey the global `command_timeout` (500 ms by default) unless `ignore_timeout` is set. Since v1.20 output is escaped; `unsafe_no_escape` opts out, and the docs warn that unescaped output (as before v1.20) can be interpreted by the shell, for example backticks executed. The config has a published JSON schema for editors. Starship's built-in modules are Rust in the core; custom commands are the only user extension (from the docs, not verified in the source).
- **Powerlevel10k** ([README](https://github.com/romkatv/powerlevel10k), [p10k-classic.zsh](https://github.com/romkatv/powerlevel10k/blob/master/config/p10k-classic.zsh), read 2026-10-23): Zsh only. A user segment is a Zsh function `prompt_<name>` that calls `p10k segment -f <fg> -i <icon> -t <text>` (the example near line 1680 of `p10k-classic.zsh`) and can be customized like a built-in (`POWERLEVEL9K_<NAME>_*`); the README's show-on-command example limits `kubecontext` to typed commands matching `kubectl|helm|kubens`. An optional `instant_prompt_<name>` is replayed before Zsh finishes loading and must make the same `p10k segment` calls. Further documentation is in `p10k help segment`. The README states the project has very limited support. Not verified: that user segments accept `SHOW_ON_COMMAND` (inferred from "customized the same way as built-in segments") and the recommended `my_` prefix.
- **What GPY takes from them:** Starship's declarative trigger, timeout, output escaping (with its pre-1.20 behaviour as the warning case), schema and `explain`-style description; Powerlevel10k's show-on-command, as a later option. Powerlevel10k's in-shell function API is the model for D.

### Measurements

macOS (arm64), Homebrew Bash 5.3.20, Zsh 5.9.2, Fish 4.9.3, macOS `/bin/bash` 3.2.57. Every run used the `tests/lib/shell_e2e.sh` sandbox: a temporary `HOME`, `XDG_CONFIG_HOME`, `XDG_CACHE_HOME` and `XDG_RUNTIME_DIR` (the variables `CliTestEnv` sets in `gpy-agent/tests/common/cli_harness.rs`) and a private `GPY_AGENT_SOCKET_PATH`; `find ~/.config/gpy -newer <marker>` listed 0 files after the last run. No prototype code is committed.

**Baseline: a Fish plugin today.** A plugin `k8s-tools` (`api_version = "v1"`, `entry_type = "file"`) whose `segments/k8s_tools.fish` renders `gpy_section_standalone blue white " PLUGIN_SEGMENT" $is_last`, enabled as `["directory", "k8s_tools", "git"]` with `theme = "text"` (checkout `00e0427`). **Proof of concept: five built-ins as plugins.** `username`, `hostname`, `clock`, `duration` and `directory` were rewritten as plugins three ways and compared with the built-in (checkout `28f2477`):

- **G**: `bin/<name>.sh` plus `segments/<id>.segment.toml` (`script`, `inputs`, `ttl_secs`, `refresh`). The adapter (95 to 118 lines per shell, the D loader included) runs `sh <script>` with the theme's `[segments.<id>]` values as `GPY_OPT_<key>` and the listed shell values as `GPY_PWD`, `GPY_HOME`, `GPY_USER`, `GPY_HOSTNAME`, `GPY_IS_ROOT`, `GPY_IS_SUDO`, `GPY_IS_SSH`, `GPY_CMD_DURATION_MS`. Output: line 1 the text (empty hides the segment), line 2 an optional colour variant (`<variant>_bg_color`/`<variant>_text_color`). One cache entry per shell and segment, keyed by those inputs; a hit reads it with builtins; the theme export changed about 60 Rust lines. These are the PoC's names; the contract in [Plugin Framework](../plugins.md#script-segments) uses `segments/<segment>.toml`, `command`, `GPY_CMD_DURATION` and no `refresh`.
- **D**: `segments/<id>.bash` (sourced unchanged by Zsh as `<id>.zsh` in all five cases) and `segments/<id>.fish`, with the `v1` names; the Bash/Zsh loader adapts the renderer's arguments to `segment_<id>_render is_last is_first`.
- **E**: the G script with `ttl_secs = 0`, run in the prompt every time.

Behaviour beyond the numbers:

- **Freshness (cached G, as prototyped).** D recomputes every prompt. The prototype's G recomputes when an input changes or the TTL expires; `directory` is keyed by `$PWD` and `$HOME`, so a change that does not move the shell (for example `git init` under `truncate_to_repo`) shows only after a `cd`. `duration` changes with every command, so G runs the script every prompt. A script can print only the time at which it ran, so the G clock needs `ttl_secs = 0`. An earlier G run (a Kubernetes-context stand-in edited in place, TTL 5 s, one Enter per second) showed the new value 3.1 / 4.4 / 3.2 s after the edit in Bash / Zsh / Fish; with the script in the background, an idle Zsh or Fish prompt still showed the old value 7 s after the edit, until the next Enter.
- **Live display.** The built-in clock hands the shell a live prompt token (`\D{}`, `%D{}`) and appears in the Zsh and Fish transient prompt; no plugin approach can do either. No approach, built-in included, repaints an idle prompt on a timer.
- **Without the agent.** With the agent disabled and stopped, Bash and Zsh drew all five segments under G, D and E; the built-in lost `directory`. In Fish, disabling the agent turns GPY off for every approach, and a stopped agent is restarted by the integration, so Fish was not testable that way.
- **Bash 3.2.** The G adapter rendered under `/bin/bash` 3.2.57 (non-interactive). D's clock needs `printf '%()T'` (Bash 4.2+) and forks `date` on 3.2.
- **Earlier background.** On a Kubernetes-context and an `$AWS_PROFILE` segment (load 11 to 37), E paid the `kubectl` script (26.7 ms alone) on every prompt, F cost one agent request per segment (+7.8 / +2.5 / +5.3 ms), E-cached matched D on a hit but showed a new directory's value only after a repaint (27-46 ms in Zsh and Fish, next prompt in Bash), kept serving old values with the agent down and after a restart, and needed agent process execution and a `Message` change; G in background mode repainted 30 to 40 ms after the prompt in Zsh and Fish. E-cached was not rebuilt for the five segments: its hit cost is the D/G file-read cost above (reused, not measured here).
- **Trigger cost.** A Starship-style trigger, evaluated by the adapter before the script, was timed on its own (2,000 evaluations, 11 directories deep, 3 file names and 1 folder checked in every ancestor, 2 extensions globbed in the working directory, 1 variable): a miss cost 204 µs in Bash, 175 µs in Zsh and 225-259 µs in Fish, a match 7 levels up 80-120 µs. Each ran with `PATH=/nonexistent`, so no external command was used: Bash `[[ -f ]]`/`[[ -d ]]` and a `nullglob` array, Zsh the same with `(N)` globs, Fish one `path filter` call over all ancestor/name pairs and one glob. That in-shell scan is not safe, though: measurement showed a `stat` on a hung NFS mount blocks every in-shell design for more than 12 s and ignores Ctrl-C, and the extension glob's `readdir` is the same kind of call (inferred). So `require_files`, `require_folders` and `require_extensions` run in a bounded child (item 6), and a false trigger on them costs one fork (+0.6 to +0.9 ms per scan on Linux, measured for files; macOS not measured). `require_env` stays fork-free.
- **Escaping.** With `promptvars` (the default), a raw `$(touch …)` and a backtick command in Bash's `PS1` both ran; after GPY's existing `__gpy_prompt_escape` (which escapes `\`, `$` and backticks; Zsh's also `%`) the same text was shown literally and nothing ran, in Bash and in Zsh with `prompt_subst`. Fish printed it literally without escaping. A pattern strip is not locale-independent: on `a`, U+009B (bytes `c2 9b`), `b`, Bash 5.3's `${x//[[:cntrl:]]/}` removed the C1 character under `en_US.UTF-8` and kept it under `LC_ALL=C`, and Fish 4.9.3's `string replace -ra '[[:cntrl:]]'` kept it .
- **Timeout constraints** . Bash 3.2.57 `read -t 0.5` fails with "invalid timeout specification"; Fish 4.9.3 `read` rejects `--timeout` and `-T`; macOS has no `timeout(1)` on the default `PATH`. Killing a timed-out `sh` does not bound the prompt: `$(sh -c 'sleep 2; echo late' & … kill)` killed `sh` at 0.2 s and the substitution still returned after 2.06 s, because the orphaned `sleep` held the pipe. Bounded runners were built in every shell anyway (below).
- **Bounded runners.** Hardened pure-shell runners (one per shell: Bash 3.2+, Zsh, Fish) and a Rust helper prototype were run against 18 hostile scripts (hangs, process trees, TERM-ignoring children, terminal readers, `setsid` escapees, 50 MB output, NUL, forged framing) on macOS, Debian (dash) and Alpine (busybox) with Bash 3.2, 4.0, 4.1, 4.4, 5.2 and 5.3, Zsh 5.9 and Fish 4. Both runners were bounded for one segment at a time: Enter to prompt p99 530-571 ms at T = 500 ms and a 50 ms grace, against a T + 50 + 30 ms limit (one of 900 macOS samples at 580.3 ms under load 20-43). Bash 3.2 is bounded sub-second (a timer job in its own process group). Ctrl-C gave a prompt within 105 ms p99 in every shell, the tree killed. The terminal's foreground group, `$!`/`$last_pid` and descriptor counts never changed, and both runners created 0 files. Per uncached run on macOS (one bench per comparison, load1 median 2.4 to 2.7, not the quiet machine asked for), the inheriting runner with the `/bin/sh` launcher skipped costs −1.85 to +1.16 ms against `$(sh script)`. Cleaning the environment costs +0.97 to +1.24 ms like for like over that runner, against a bar of +0.5 ms, so the measurements favoured inheriting. The maintainer chose cleaning anyway, so that undeclared variables cannot make cached output stale and credentials do not reach scripts by default. The chosen shape (clean, launcher skipped) costs +0.07 to +0.30 ms over today's unmodified runner, and +0.67 to +0.89 (Bash), +0.88 (Zsh) and +2.41 ms (Fish) over `$(/bin/sh script)`. It was priced with a fixed locale list (`LC_ALL`, `LC_CTYPE`, `LC_MESSAGES`); the contract's "every set `LC_*`" was not priced. On Linux the runner adds +0.4 to +0.9 ms; cleaning cost +0.04 to +0.18 ms in a process-level loop, not the harness, and Linux Fish's `env -i` was not built. Survivors: only a `setsid`/daemonizing escapee; in a container whose PID 1 does not reap, orphans become zombies. Placement was measured in GPY's real hooks with a stub runner: one run for the first prompt and one per command; none on an empty Enter, Ctrl-C, the SIGURG repaint, SIGWINCH or the transient prompt.

Not measured: Unicode cluster abbreviation in `directory` (G and D take the first character, not the grapheme cluster, so they probably differ); `read_only`; the real runner inside GPY's hooks; several segments sharing one deadline (not built); KILL for leftovers after a normal exit (not built); the macOS scan-child cost and a macOS mount stop; a `stat` in uninterruptible sleep; the scan on macOS NFS, SMB or autofs, FUSE, `soft` mounts, mount tables over 215 lines and WSL `/mnt/c`; the trigger inside the full adapter (timed alone above); show-on-command (not built); a theme switch in Bash and Zsh under D or G; many plugin segments at once; Fish repaints per prompt in a git repository; Fish without the agent; Bash 4.2, 4.3, 5.0 and 5.1; Fish 3.x (3.6 is the supported floor; every Fish run was 4.x); Zsh 5.8; user options (`set -u`/`-e`, bash-preexec, `PROMPT_COMMAND` arrays); a `--pids-limit` container; Fish's `none` wrapper mode (no `setsid(1)` and no `/bin/bash`, so only the direct child is signalled); the Fish cap and clean environment on Linux; memory.

### Dogfooding and examples

- **Will run on G (dogfooding):** `username` and `hostname` (static per session; on a cache hit about 6 times cheaper than the template-rendered built-in in Bash and 2 to 3.5 times in Zsh and Fish, from the table above). Decision item 2 takes one or both of them onto G.
- **Run at parity on G at E's cost:** `directory` and `duration`. Their input changes every directory or command, so G runs `sh` on each such prompt, cached or not; as D they are fork-free and always fresh, which is the case D is kept for. They stay built in.
- **Must stay native:** `clock` (live prompt token, transient prompt).
- **Contract gaps** (what the public contract must expose before built-ins or third parties can rely on it): public names for shell state (`is_root`, `is_sudo`, `is_ssh`, the last command's duration; D read `__gpy_is_*` and `__gpy_cmd_duration`); colour variants (D read `__color_<id>_user_bg`); the glyph mode (a private-use icon over SSH was dropped by the built-in with `show_icons = false` and printed by every plugin); the theme's `format` for a plugin segment (or a stated rule that plugins are pills; the `text` theme differences and the username icon spacing, `⚡jpease` vs `⚡ jpease`, come from this); typed plugin settings (core config and built-in themes are typed, but a plugin's `[segments.<id>]` values are an undeclared string map, so `"3"` and `"true"`, and plugins cannot read `config.toml`); live prompt tokens and transient-prompt participation.
- **What the examples teach an author:** how a segment receives settings (`GPY_OPT_*`) and shell values (`GPY_*` inputs), the two-line output protocol, choosing `ttl_secs` and `refresh` (`username`/`hostname`: one run per session; `directory`: per directory; `duration`: per command; `clock`: why a script is the wrong tool), and that GPY draws colours, caps and separators. The G examples needed no GPY internal; the D files did (the gaps above).

## Decision

Accepted by the maintainer (2026-10); amended the same month (see Status). Accepting the amendment approves the direction only: every implementing PR that crosses an approval boundary (item 9) still gets explicit maintainer review at that point.

1. **Now: Option B.** Say "plugin segments written as Fish files (`entry_type = "file"`) load in Fish only" in [Build a Segment Plugin](../build-segment-plugin.md), [Plugin + Theme Authoring](../plugin-theme-authoring.md) and the [developer docs index](../README.md) ([Plugin Framework](../plugins.md) already says Fish-only); add a row for them to the [shell feature matrix](../../INSTALL.md#shell-feature-matrix) and narrow its opening sentence to the built-in segments; print one line in `gpy plugin new`, `validate` and `list`; and at `gpy enable <segment>` for such a segment with a Bash or Zsh integration installed, note that those prompts skip it, with the remediation `gpy disable <segment>` or use Fish. Every message names `v1` `.fish` segments, so it stays true when G lands; the G adapter work then narrows the docs by adding that script segments render in all three shells.
2. **G is a core feature of GPY.** One POSIX script and a manifest per segment serve all three shells with no GPY internal and no agent involvement. It is the cross-shell plugin format and also an engine for GPY's own segments:
   - **Dogfooding, one or two built-ins at most:** `username` and/or `hostname`, shipped with GPY as G segments. Acceptance bar: the PoC parity method (styled cells, `default` and `text` themes, three layouts, three shells) with no difference left except ones the contract-gap work has closed, and a render no slower than the built-in it replaces in each shell. `directory` and `duration` stay built in (D-class: fork-free and fresh every prompt); the clock stays native. D is not chosen: it stays a measured, documented alternative, and no D loader is committed.
   - **Plugin identity.** A G plugin has its own `entry_type` (for example `"script"`; `EntryType` has only `file` and the reserved `command` today, `plugin/manifest.rs:171-176`). With `entry_type = "file"`, `validate_plugin_root` requires `segments/<id>.fish` for every segment (`commands/plugin.rs:66-77`); the G branch checks the segment manifest and the contained script instead. `min_gpy_version` (`manifest.rs:298`) is today only a printed warning in `gpy plugin validate` (`commands/plugin.rs:167-182`); it becomes enforced: export and `validate` reject a plugin whose minimum exceeds the running GPY.
3. **Cache on by default, short TTL, in shell variables.**
   - **Once per command, not per draw.** A G segment is **due** on the first prompt, after a new command, or when `PWD` changed since its last run; then it runs if its TTL expired or its key changed. It is never due on a repaint, an empty Enter that leaves `PWD` unchanged (a key binding that runs `cd` makes the next prompt due), Ctrl-C, the SIGURG doorbell (`fish/core/ipc.fish:1212-1225,1250-1252`) or SIGWINCH. A Ctrl-C during a run hides the segment for that prompt without rerunning it.
   - **The author sets `ttl_secs` in the segment manifest; default 5.** A hit cost 1.5 to 1.6 / 1.6 to 1.8 / 2.7 to 2.8 ms against 7.1 to 8.7 / 5.8 to 7.2 / 6.7 to 8.0 ms for a one-process run (PoC G "Hit" and E rows, reused, not re-run), and at one Enter per second a TTL of 5 s showed an edited value 3.1 to 4.4 s later (Measurements): staleness of about one or two commands, for a hit that costs a fifth to two fifths of a run. `ttl_secs = 0` opts out (one run per command that passes the trigger), for segments that must be current; a segment whose output depends only on its inputs (`username`, `hostname`) sets a TTL longer than a session. The user overrides `ttl_secs` per segment (item 4). A change outside the key shows only after the TTL, and only when a prompt is drawn; nothing repaints an idle prompt.
   - **Placement.** Runs happen in the interactive shell, never in a render subshell: Bash in `__gpy_precmd` before `__gpy_render_prompt`; Zsh in `__gpy_precmd` before `__gpy_update_prompts`, with `__gpy_preexec` setting the due flag and a local `TRAPINT`; Fish in an `--on-event fish_prompt` handler, with a `fish_postexec` handler that only sets the due flag (a run inside the `fish_prompt` function drew no prompt after Ctrl-C). Zsh renders inside `$(__gpy_render_prompt …)`, so a guard or cache set there is lost with the subshell; the render subshell and repaints only read the results. Results are known before the render loop, so `_detect` is a fork-free "result is non-empty" test and `is_first`/`is_last` are fixed correctly.
   - **Storage and key.** The guard and the cache are shell variables in the interactive shell: no files of any kind, nothing outlives the shell. The key holds the plugin id and version, the segment id, the script path, the resolved `GPY_OPT_*` values, the values of the **declared inputs** and the values of the **declared `env` names**, and nothing else. Scope follows from them: **session** when `pwd` is not declared (`username`/`hostname` run once per session), **folder** when it is. There is no device scope; it would need a file. The age comes from a clock in the same shell (`$SECONDS`/`EPOCHSECONDS`; the Fish clock source is open).
   - **Sanitize once.** The runner caps, strips and escapes the output before any shell variable holds it (item 5 and the [script segment security addendum](adr-0011-addendum-script-segment-security.md)); the cache holds the render-ready value and raw output is never stored.
   - **E stays rejected.** E runs a program on every prompt with no trigger and no cache; G's default caches, skips prompts where the trigger fails, and never runs more than once per command. `ttl_secs = 0` is E behind a trigger, chosen per segment and paid against the budget (item 7).
4. **Typed plugin settings and the user override.** Core `config.toml` and the built-in segment themes are typed (serde with validating newtypes; `[segments.duration] show_if_exceeds_ms` is a `u64`). Plugin segments are not: unknown `[segments.<id>]` tables land in `SegmentThemes.plugin` (`gpy-agent/src/theme/model/mod.rs:65-67`, a serde flatten catch-all) and their extra keys in `PluginSegmentTheme.properties: HashMap<String, String>` (`mod.rs:88-90`), so a non-string value cannot deserialize and nothing declares a setting's type, range or default.
   - The segment manifest declares each setting: `bool`, `int` or `string`, a default, a range or choices, and a description, the shape of a `ConfigKeyMeta` entry in `CONFIG_KEYS` (`config/metadata.rs:23-56`) plus a type. `ttl_secs` and `timeout_ms` are reserved manifest fields, not settings. Values reach the script as strings; the gain is validation at load, naming the key, as core config does. `gpy plugin validate` checks the manifest against a published JSON schema with a drift test.
   - **The user override lives in `config.toml` under `[plugin.<segment>]`**, which [PR #52](https://github.com/jpease/gpy/pull/52) added; `gpy config get/set/list` reach it as `plugin.<segment>.<key>`. Settings are behaviour, not style: in the theme they would be lost on every theme switch and could be changed only by copying a whole theme (`gpy theme new`). Theme `[segments.<id>]` keeps style keys only.
   - **MAJOR** under `gpy-agent/SCHEMA_EVOLUTION.md` (field type change): settings leave the theme's string map and become typed values elsewhere. Acceptable before announcement; no shim, and older GPY versions are not considered.
5. **Trust model and hardening.** The user installs a plugin by placing its directory in the user plugin root (`$XDG_CONFIG_HOME/gpy/plugins/`; or a bundled directory, `plugin/registry.rs:65-89`) and enabling a segment; GPY downloads nothing. A G script then runs as the user once per command that passes its trigger, including in untrusted directories (a cloned repository, an unpacked archive) whose names and files it receives as input. The script itself runs in a child `sh` and cannot change the shell's variables or functions, but the adapter around it runs in the interactive shell: in Bash 3.2 and 5.3, `${!n}` with `n='a[$(cmd)]'` ran `cmd` (run 2026-10-23), and the review showed the PoC adapter open to that and to globbing. Required:
   - **What the script sees.** A clean environment: `PATH` without empty, `.` or other relative entries, `HOME`, `USER`, `LOGNAME`, `LANG`, every set `LC_*`, `TERM`, `TZ` and `TMPDIR`, plus the declared `env` names and the `GPY_*` inputs and `GPY_OPT_*` settings the runner sets (a user-exported `GPY_OPT_*` never reaches it). Credentials, `SSH_AUTH_SOCK` and exported functions are absent unless declared; this is hygiene and cache correctness, not a confidentiality boundary. stdin and stderr are `/dev/null`; cwd is the plugin root unless `pwd` is declared; the script runs in its own process group (or session) and never gets the terminal. The interpreter is `/bin/sh` by an absolute path resolved once (on macOS the shell `/private/var/select/sh` points to, run as `sh`, skipping the launcher); in Zsh a bare `sh` cost 1.8 ms more per run than `/bin/sh`, probably because each run repeats the `PATH` search (inferred). The `require_command` script gets the same environment, working directory, interpreter and process rules.
   - Every variable name the adapter builds is a fixed prefix plus a name the merged contract types allow: the segment token (segment names `^[a-z0-9_-]+$` with `-` turned into `_`, token collisions rejected), `env` names `^[A-Za-z_][A-Za-z0-9_]*$` (ASCII, no locale ranges), setting keys `^[a-z_][a-z0-9_]{0,63}$`, and a fixed list of inputs. Discovery checks them, and the shell checks the complete name against `^[A-Za-z_][A-Za-z0-9_]*$` before any indirect expansion; adapters never pass names or values through `eval`-like forms (`${!n}` on an unchecked name, `eval`, Zsh `${(P)…}`) or unquoted expansions that glob. Declared values reach the script byte for byte.
   - **Output, once at the runner boundary.** Cap at 4096 bytes, counted in bytes (over the cap hides the segment; the cap comes before the strip; 4096 is a decision, the spike runners capped at 64 KiB). Strip every C0 control and DEL (U+0000 to U+001F, U+007F) by ranges, not `[[:cntrl:]]` (per the Measurements finding), in Fish too. Then hide the segment if a C1 control (U+0080 to U+009F) remains: removing bytes can join their neighbours into a C1 character, so C1 is checked, not stripped (addendum). Then escape for the drawing shell: Bash `\`, `$` and backticks; Zsh the same plus `%`; Fish nothing beyond the strip. Escaping is not idempotent, so it happens once; the cache stores that value. Output must not contain NUL; text after a NUL may be lost. Starship before v1.20 is the cautionary case.
   - The `command` and `require_command` paths resolve under the plugin root (absolute paths, `..` and symlinks leaving it rejected), enforced by `ScriptSegmentManifest::load`, which discovery and `validate` both call.
   - SECURITY.md ("Plugin segment files run as you") changes with the adapters. "Bash and Zsh never source them" stays true of `.fish` files, but G scripts are executed, not sourced, by Bash, Zsh and Fish; the paragraph must say so, state the per-command, untrusted-directory exposure and the hardening above, and keep "trust it like a shell startup file" for all three shells.
6. **Timeout, kill rules and scan bound** (parts not built or not measured are marked). The runner is **pure shell**, one per shell, inside a `$( )` (Bash, Zsh) or a child `sh` wrapper (Fish), with no files and no descriptor left open after a run; `require_command` runs under the same runner and deadline and counts toward the breaker like the script. In the rules below, T is the segment's `timeout_ms` and G the 50 ms grace.
   - **Timeout.** `timeout_ms` per segment, default and maximum 500: the author may lower it, and the user may lower it further in `[plugin.<segment>]` (a value above the manifest's is rejected). One shared deadline per prompt, fixed at 500 ms from the first due segment's start and not configurable; a segment not finished before it is deadline-skipped: hidden for this prompt, due again on the next. The shared deadline is not built: Bash 3.2-4.4 and Fish have no clock to share serially and need a batch mode in the runner. Without it, N hung segments run one after another hold the prompt about N × (T + G) (inferred).
   - **Kill rules.** On timeout or Ctrl-C: TERM, then CONT, to the script's process group, KILL after G or as soon as the script itself exits; never wait for pipe EOF (measured in every runner). On a normal exit, if members remain in the group, TERM and CONT, then poll `kill -0 -PGID` for at most G and send KILL, synchronously before the prompt, waiting only when members remain. The spike runners sent TERM and CONT only; the KILL step is not built or measured.
   - **Circuit breaker.** Two consecutive timeouts (of the script, `require_command` or the scan) or cap overflows disable the segment for this shell, with one stderr line, once. N = 2 is a decision, not a measurement. A success, a scan that completes (match or miss), the reload doorbell or a new shell resets it. Deadline-skipped runs, Ctrl-C and a non-zero exit do not count.
   - **Scan bound.** `require_files`, `require_folders` and `require_extensions` are checked in one child with a 30 ms deadline, killed with SIGKILL (only a fatal signal ends a blocked NFS `stat`); a timeout hides the segment like a miss. The child uses cwd-relative paths (`Chart.yaml`, `../Chart.yaml`, …) and, on Linux, stops at the mount holding `$PWD`, read from `/proc/self/mountinfo` (the Fish child's dash loop took 22 ms at 215 lines, so hosts with many more mounts need another method, not measured). macOS has no `/proc`, so there the search goes up to `/` and only the deadline bounds it; the contract states the difference. The child's PID comes from the child itself, never from `$!`; on Bash before 4.1, which has no `{fd}`, its descriptor is closed before the prompt. Helpers run by absolute path; Fish starts it with `env -u PWD` because dash stats `$PWD` at startup.
   - **Documented gaps.** A `setsid` or daemonizing escapee survives; in a container whose PID 1 does not reap, every timed-out run can leave zombies (run with `--init`); a `stat` in uninterruptible sleep may outlive the killed scan child (not reproduced; whether the prompt stays bounded then is unproven); a slow but healthy file system (WSL `/mnt/c`, cold NFS) or a large mount table can time out every scan and trip the breaker (not measured).
   - **Revisit a Rust helper** (`POSIX_SPAWN_SETSID`, a Linux subreaper) only if one of these holds. Timing conditions are judged on p99 over at least 300 Enters per shell, with the load average recorded. (1) A pure-shell batch with one shared deadline cannot hold p99 ≤ T + G + 30 ms for 3 segments in Bash 3.2-4.4 or Fish, on macOS or Debian. (2) Evaluated on macOS, does not hold: Fish's over-cap error is suppressed in the child for +0.62 ms (`fdrain`: `head -c 4097` in the wrapper, outside the script's group), so the Fish cap uses that shape; the Linux Fish wrapper is `sh`, which has no process substitution, and the Linux form is not built. (3) Evaluated, does not hold: at load1 median 2.7 (the < 2 asked for was not reached), pure-shell Fish was +1.16 ms and Zsh −1.85 ms with the launcher skip, at most +0.13 ms above the helper; a quiet-machine run is still owed. (4) In GPY's real hooks, a hostile script leaves no prompt, runner text on the terminal or an undocumented survivor with pure shell where the helper does not, or a "no prompt until Ctrl-C" hang appears in 200 runs of the hang set. (5) and (6) are maintainer choices, not measurements: containers with a non-reaping PID 1 become a supported target; or the maintainer prefers one implementation and approves `unsafe`, run-time process execution in Rust and a third binary.
7. **Performance.** The PoC's five built-ins render in 35.88 / 13.13 / 20.67 ms (Bash / Zsh / Fish); `tests/performance-baselines.json` targets 37 (`prompt_render_bash`), 13 (`prompt_render_zsh`) and 20 ms (`prompt_render`, the warm `fish_prompt` render), with maxima 111, 39 and 50. A G hit adds 1.5 to 2.8 ms and a one-process run 5.8 to 8.7 ms, so one segment passes the Zsh target even on a hit and every target on a run; three G segments expiring on the same command add about 17 to 26 ms (arithmetic on reused PoC numbers; a variable-cache hit is not measured but should not cost more than the PoC's file read). The chosen runner (clean environment, launcher skipped) adds +0.67 to +0.89 (Bash), +0.88 (Zsh) and +2.41 ms (Fish) per uncached run over `$(/bin/sh script)` on macOS (one bench, load1 median 2.4; the clean environment's own share is in Measurements), and +0.4 to +0.9 ms on Linux plus +0.04 to +0.18 ms for cleaning (process level). A due prompt with a `require_files`, `require_folders` or `require_extensions` condition pays one scan child, +0.6 to +0.9 ms on Linux (macOS not measured). On Bash 3.2-4.3 an enabled G segment installs a DEBUG trap, +5.94 µs per command. `scripts/ci-bench.sh` renders the configured built-in segments in every shell and no plugin segment, so the adapter work adds a G scenario (hit, expiry, and the scan child) with a budget per shell, Fish included, and states any target change for review. Moving `username`/`hostname` onto G lowers the prompt in each shell (hits of 1.5 to 2.8 ms against 3.5 to 9.3 ms built-in).
8. **Trigger semantics.** G keeps its rule: every condition must hold; files and folders are searched from the working directory upwards, up to the mount that holds it on Linux and up to `/` on macOS (item 6); extensions in the working directory only; the command condition (`require_command`) runs only after the others pass. `require_env` is fork-free; `require_files`, `require_folders` and `require_extensions` cost one bounded child per due prompt, so a false trigger on them is no longer free. An any-of rule would run the command on every prompt where the file checks miss, and project segments need the upward search. Starship's names mean something else (any one condition; working directory only), so G does not reuse them: `require_files`, `require_folders`, `require_extensions`, `require_env` and `require_command`. The Starship importer therefore cannot map `[custom.*]` mechanically and keeps skipping it with its warning (`import/starship/layout.rs:63`); translating the cases where the meanings coincide is a later item.
9. **Approval boundaries** (changes that need explicit maintainer approval) the work crosses, each needing explicit approval in its PR: adding external process execution (the shells run scripts, `require_command` and the scan child; the CLI runs a syntax check and `doctor` timing); file path validation (script containment); the Fish shell integration contract (the loader branch, the event-handler placement and once-per-command reuse across repaints); configuration schema structure (the `config.toml` table, typed settings, the manifest entry type). The pure-shell runner adds no boundary beyond these.
10. **Implementation order**, each a separate work item: (1) B, as its own PR; (2) the contract: public shell-state names, colour variants, glyph mode, plugin `format` or the pill rule, G `entry_type`, enforced `min_gpy_version`, name validation, typed settings, the `config.toml` override and the published schema (done, [PR #52](https://github.com/jpease/gpy/pull/52)); (3) the timeout and scan spike (done; item 6); (4) G adapters in Bash, Zsh and Fish with the runner, placement, cache, trigger, scan child, output rule, containment, SECURITY.md change and `ci-bench` scenario; (5) tooling: `gpy plugin new` (scaffold), `validate` (schema, each segment's `description` as `starship explain` shows it, a syntax check with `dash -n` or `shellcheck -s sh` where installed, since macOS `/bin/sh` is Bash 3.2 and accepts bashisms), `doctor` (time the script), `list` (show the format); the examples include one segment that is not a built-in (a Kubernetes context or AWS profile); (6) dogfood `username`/`hostname`; (7) narrow B's docs.
11. **Later, not measured:** `show_on_command = "kubectl|helm"` in the manifest, showing a segment only while the typed command matches. Zsh can redraw while typing through a line-editor hook (`zle-line-pre-redraw`, `zle reset-prompt`), as Powerlevel10k does; Fish would need a key binding that repaints; Bash's readline offers no supported way to redraw the prompt while typing, so it would apply in Zsh and Fish only.

E-cached is not pursued: on these segments it would match a cached G hit but needs agent process execution, a `Message` change and cache invalidation, and goes stale without the agent. F is not a plugin format for these segments: four of the five need logic the template engine lacks.

## Alternatives Considered

### Option A

Fish-only, with the existing CLI-reference note. No cost, but it contradicts the cross-shell premise and leaves the silent drop shown in the baseline.

### Option B

Docs and messages, as in Decision item 1. No prompt-time cost and no change to shell scripts, IPC or `v1`. The `gpy enable` note reuses `setup::installed_integrations()`, which only checks that `$XDG_CONFIG_HOME/gpy/<shell>/` holds an entry point (`gpy-agent/src/commands/setup.rs:261-279`), so it can name a shell that is installed but unused. A mitigation, not cross-shell support.

### Option C

A `gpy doctor` warning per enabled plugin segment, from `enabled_plugin_segments` (`doctor.rs:280`) and `installed_integrations()` (`doctor.rs:46`). Keyed on installed integrations it has B's false positive inside a health report; keyed on the current shell (`GPY_SHELL`, then `$SHELL`) it misses a Fish user who also runs Bash. An optional add-on to B only if the `gpy enable` note proves insufficient.

### Option D

Port the loader: the theme export names a `.bash`/`.zsh`/`.fish` file per segment, and the Bash and Zsh loaders adapt the renderer's call to the `v1` `segment_<id>_render is_last is_first` (about 15 lines per shell on top of a public `gpy_section_standalone`). Measured above: the cheapest plugin approach in every cell, fork-free except Fish's `date`, always fresh, works without the agent. Privilege: plugin code is sourced into Bash and Zsh as it is into Fish today. Lost: authors maintain a Bash/Zsh file and a Fish file (the `directory` Fish file was a 104-line rewrite) and today must read GPY internals. `v1`: additive. Not chosen: deferred until a segment needs to be fresh and fork-free on every prompt.

### Option E

Activate `entry_type = "command"`. Uncached, the shell runs the program every prompt: measured at 6 to 10 ms per render with one segment and one process per segment, with no trigger and no cache; rejected (Decision item 3 says how G's default differs). E-cached (agent runs it off the request path, caches, repaints through SIGURG) was measured on the earlier Kubernetes segment only: hit cost equal to D, the value one repaint late on a new key, stale with the agent down, and approval-gated (external process execution from the agent, a `Message` variant, new path validation, a dependency from `plugin` on `ipc::registry`).

### Option F

Declarative trigger plus template rendered by the agent. Measured earlier at one agent request per segment per prompt. On the five segments: `username` needs a style chosen by root state (the built-in's `format`/`user_format` split); `hostname` needs `trim_at`, a string operation the template engine lacks; `duration` needs arithmetic formatting; `directory` needs the 312-line resolver; `clock` needs the per-shell live token. Each needs a new agent-side data source or transform, which is the built-in again.

### Option G

One portable script per segment, run by each shell behind a declarative trigger, cached in shell variables for a short TTL by default (measured above). Privilege: the script runs as the user from the shell, like D's code, in a child `sh` that cannot change the shell's variables or functions, while the adapter that feeds it manifest names and values runs in the interactive shell; it gets a clean environment plus declared names and runs in untrusted directories; the prototype had no timeout and inherited the whole environment (Decision items 5 and 6). It adds no agent process execution, no `Message`/`Response` change and no `security.rs` change, but crosses four approval boundaries (Decision item 9). Tooling: `gpy plugin new` scaffolds `bin/<segment>.sh` and `segments/<segment>.toml`; `validate` checks the manifest against the published schema, prints each segment's description and syntax-checks the script; `gpy doctor` times it; `gpy plugin list` shows the format. `v1`: the manifest gains an entry type and an enforced minimum version, breaking where needed before announcement. Chosen, as a core feature.

## Consequences

### Positive

- B removes the silent surprise now.
- One script per segment renders in Bash, Zsh and Fish, with no GPY internal and no agent involvement, and can carry GPY's own static segments at a fraction of the template-rendered cost.
- Cached by default in shell variables, a G segment runs at most once per command and stays within one TTL of fresh; a `require_env` trigger keeps it free on prompts where it does not apply, and the file conditions cost one bounded scan child; no cache file exists to go stale across shells or to be planted.
- Plugin settings get the declared types and load-time validation that core config already has, and the user's override survives a theme switch.

### Negative

- Only G is introduced, not two formats. D is deferred, so a segment that must be fresh and fork-free on every prompt has no plugin route until D is taken up.
- A run costs one `sh` (about 6 to 9 ms per render in the PoC) on each command after the TTL, or every command with `ttl_secs = 0`; otherwise output is stale up to the TTL. One segment can push a shell past its render target; the G scenario and budgets in `ci-bench` make that visible.
- A public contract had to come first: shell state, colours, glyph mode, G `entry_type`, enforced `min_gpy_version`, and typed settings in a new `config.toml` table, a MAJOR configuration schema change ([PR #52](https://github.com/jpease/gpy/pull/52)).
- SECURITY.md changes: plugin code now runs from Bash and Zsh as well as Fish, on every command, in untrusted directories; the hardening in Decision item 5 is required, not optional.
- The timeout is bounded for one segment in every shell, Bash 3.2 included, at p99 within T + 50 + 30 ms in the spike's runners; it was not run inside GPY's hooks, and several segments need the shared deadline, which is not built. Documented gaps: a `setsid` or daemonizing escapee survives, containers without a reaping PID 1 collect zombies (`--init` required), and an uninterruptible `stat` may outlive the scan child. The margin is thin under heavy load (worst sample 580.3 ms against 580 ms).
- Three runners, one per shell, with platform traps (dash `kill -SIG -PGID`, no `set -m` in `sh`, Bash 3.2 parse quirks) and a CI matrix with dash, busybox and Bash 4.x to keep them honest.
- G's trigger names differ from Starship's on purpose, so imported Starship configs still lose their `[custom.*]` modules.
- Plugins remain pills unless the contract adds `format`, and the clock cannot be a plugin.
- B and G are production code, each tracked as a separate work item, and four of the G items need explicit approval.
